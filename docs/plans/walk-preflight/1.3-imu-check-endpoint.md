# User Story 1.3: Expose the IMU probe at `POST /api/imu/check`

## Story

**As a** Studio connect flow
**I want** an endpoint that says whether the duck's IMU answers
**So that** an unplugged IMU is caught at connect, before anyone presses Walk

## Background

Studio's duck setup has one check today, `wake-motors`, backed by `POST /api/motors/check`
(`scripts/tnkr_server.py:751`). Nothing tests the IMU until the walk's constructor does.
Story 3.1 adds a `wake-imu` `CheckStep` to the duck manifest in Studio; this story gives it
something to call.

Builds on 1.2: the endpoint is `_preflight_imu()` exposed on its own route, shaped like
the motors check: 200 with a small body on success, the coded 502 on failure. An older
agent without this route returns 404, which Studio's `_STATUS_TO_CODE` already maps to
`AGENT_OUTDATED` and its existing upgrade sentence.

## Acceptance Criteria

### Core Functionality

- [ ] **Route**: `POST /api/imu/check` returns `{"present": true}` when `get_state_imu()`
      succeeds.
- [ ] **Refuses while walking**: `refuse_while_walking()` first, as every idle bus/I2C
      route does. The walk owns the I2C then.
- [ ] **Coded failure**: any exception from `get_state_imu()` becomes
      `_agent_error(502, "IMU_NOT_FOUND", f"{type(exc).__name__}: {exc}")`, identical to
      the pre-flight's classification.
- [ ] **Shared handle**: the endpoint reuses `get_state_imu()`; it never constructs an
      `Imu` of its own, so a running IMU calibration (which shares the handle, `:2603`)
      is not reset by a check.

### User Experience

- [ ] **Fast**: a dictionary lookup when the handle exists; ~0.75 s when it has to be
      constructed.
- [ ] **Idempotent**: calling it repeatedly has no effect on the chip's state beyond the
      first construction.

### Technical Requirements

- [ ] **Telemetry**: `add_telemetry_props(imu_present=True)` on success; on failure
      `error_code="IMU_NOT_FOUND"` and `error_type` as in 1.2. Not in
      `TELEMETRY_EXCLUDED_PATHS`; it is a deliberate check, not a poll.
- [ ] **Studio parity is 3.1's job**: `sim_agent.py` and the fake agent gain the route in
      the Studio repo, not here.

## Expected User Flow

```bash
$ curl -s -X POST localhost:8000/api/imu/check
{"present":true}

# IMU unplugged
$ curl -s -X POST localhost:8000/api/imu/check
HTTP/1.1 502
{"detail":{"code":"IMU_NOT_FOUND","message":"ValueError: No I2C device at address: 0x28"}}

# while a walk is running
HTTP/1.1 409
{"detail":"The walk owns the servo bus — stop it first"}
```

### Key Dependencies

- **`_preflight_imu()`** from 1.2, factored so both the pre-flight and the route call it.
- **`refuse_while_walking()`** at `:310`.

### Core Functions to Implement

```python
# scripts/tnkr_server.py

@app.post("/api/imu/check")
def imu_check() -> dict:
    """Does the BNO055 answer? The connect-time half of the walk pre-flight."""
    refuse_while_walking()
    _preflight_imu()                 # raises 502 IMU_NOT_FOUND
    add_telemetry_props(imu_present=True)
    return {"present": True}
```

### Technical Considerations

#### Interaction with IMU calibration

- The calibration worker holds `get_state_imu().imu` for its whole run. A check during a
  calibration reuses the same object and reads nothing from it, so it cannot disturb the
  calibration's mode. It does not need `_imu_lock`.

#### Error Scenarios to Handle

- Walk running: 409 from `refuse_while_walking()` (plain string, mapped to
  `INVALID_STATE` by Studio, as every other idle route).
- Rehome session open: not a conflict; the IMU is on I2C, not the servo bus. No guard.
- Chip absent or bus down: 502 `IMU_NOT_FOUND`.

#### Performance & UX

- Under 10 ms with an existing handle; well inside the 10 s `timeout_ms` story 3.1 gives
  the step.
