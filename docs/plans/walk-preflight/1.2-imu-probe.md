# User Story 1.2: Refuse a walk when the IMU is missing

## Story

**As a** duck operator pressing Walk
**I want** the agent to confirm the IMU answers before the walk starts
**So that** an unplugged IMU is named on screen instead of the walk dying rigid in its crouch

## Background

This is the incident. Seven walks on one duck (2026-09-02 to 09-08) reached the crouch,
applied full gains, slept two seconds, and died at `raw_imu.py:43-44` where the walk
constructs its own `BNO055_I2C` and nothing answered at 0x28. The cleanup that cuts torque
lives in `run()`, which was never reached, so the duck stayed stiff. Studio never saw more
than `exit_code: 1`.

Builds on 1.1: adds the IMU half to `_walk_preflight()`, after the servo roll-call. The
probe is `get_state_imu()` (`scripts/tnkr_server.py:317`), which constructs the shared
handle or returns the existing one. It must **reuse** that handle, not build a second
`Imu`: the adafruit constructor soft-resets the chip (`SYS_TRIGGER 0x20`) and wipes the
axis remap, as the comments at `:319-327` and `:2603` warn. Running before
`release_state_imu()` (`:2958`) is what makes reuse possible.

One code only, `IMU_NOT_FOUND`, for the constructor failing. A chip that answers its
identity check but yields no readings is a real state and is **deferred** (architecture,
Alternatives, decision 2026-09-09). The probe therefore does not wait on a sample.

## Acceptance Criteria

### Core Functionality

- [ ] **Probe after servos**: inside `_walk_preflight()`, once the roll-call passes, call
      `get_state_imu()`. Servos first: a silent servo reports as `MOTORS_SILENT` even if the
      IMU is also missing.
- [ ] **Constructor failure refuses**: any exception from `get_state_imu()` produces
      `_agent_error(502, "IMU_NOT_FOUND", f"{type(exc).__name__}: {exc}")`. Covers
      `ValueError("No I2C device at address: 0x28")`, `RuntimeError("bad chip id ...")`,
      and `OSError` from a bus that is not up.
- [ ] **No sample wait**: the probe does not block on `get_data()`. A fresh handle costs
      the constructor's own ~0.75 s and nothing more.
- [ ] **Handle left in place**: on pass, `state_imu` remains set so the existing
      `release_state_imu()` call at `:2958` runs as today and the walk constructs its own.
- [ ] **Report filled**: `PreflightReport.imu_present` is `True` on pass.

### User Experience

- [ ] **Refusal is immediate**: under 1 s on a healthy duck, about 1.75 s when the IMU
      handle has to be constructed first.
- [ ] **Studio unchanged in this story**: an older Studio maps an unknown 502 to
      `AGENT_FAILED`; story 2.1 adds the code and 2.2 the sentence.

### Technical Requirements

- [ ] **Telemetry on refusal**: `add_telemetry_props(error_code="IMU_NOT_FOUND",
      error_type=<exception class>, preflight_ms=<int>)`.
- [ ] **Telemetry on pass**: `imu_present=True` alongside 1.1's props.
- [ ] **Existing tests keep passing**: `fake_walk_dir` installs a `FakeStateImu` via
      `monkeypatch.setattr(tnkr_server, "get_state_imu", ...)`, the seam
      `tests/test_imu_calibrate.py:45` already uses.

### Key Dependencies

- **`get_state_imu()`**: the shared BNO055 handle, lazily constructed.
- **`raw_imu.Imu`**: constructor raises when the chip is absent; nothing else is touched.

### Core Functions to Implement

```python
# scripts/tnkr_server.py

def _preflight_imu() -> None:
    """Confirm the BNO055 answers, by constructing or reusing the state IMU.

    Raises via _agent_error(502, "IMU_NOT_FOUND", ...) with the exception class and
    message for the developer. Never builds a second handle: a second constructor
    soft-resets the chip and wipes the axis remap."""
    try:
        get_state_imu()
    except Exception as exc:
        add_telemetry_props(error_code="IMU_NOT_FOUND", error_type=type(exc).__name__)
        _agent_error(502, "IMU_NOT_FOUND", f"{type(exc).__name__}: {exc}")
```

### Technical Considerations

#### Why the constructor is the whole test

- **Identity check is inside it**: the adafruit driver reads the chip id and raises if it
  is not `0xA0`; Blinka's `I2CDevice` probe raises `ValueError` if nothing acknowledges.
  Those two exceptions are the two ways a cable shows up.
- **No sample wait, by decision**: a freshly constructed sensor legitimately returns
  `None` for its first second. Waiting would misreport a healthy IMU; not waiting means a
  chip that hangs after identifying itself still gets through. That case is deferred and
  the raw `error_message` on the walk's eventual failure will show whether it occurs.

#### Error Scenarios to Handle

- `ValueError("No I2C device at address: 0x28")`: nothing wired.
- `RuntimeError("bad chip id (0x0 != 0xa0)")`: something else at the address, or a
  corrupted read.
- `OSError` / `RuntimeError` from `busio.I2C(...)`: the I2C bus is not enabled.
- `ImportError` from `board` / `adafruit_bno055` on a non-Pi host: cannot happen on the
  `is_pi` path; the mock path never runs the probe.

#### Performance & UX

- Existing handle (Studio has been polling `/api/state`): a dictionary lookup.
- Fresh handle: ~0.75 s (adafruit soft reset + 0.7 s wait). Still under the "feels like a
  press" budget together with 1.1.
