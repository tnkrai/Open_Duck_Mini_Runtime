# User Story 1.1: Refuse a walk when a servo is silent

## Story

**As a** duck operator pressing Walk
**I want** the agent to check every servo answers before the walk starts
**So that** a loose servo cable is named on screen instead of the walk dying in its crouch

## Background

Today `POST /api/walk/start` (`scripts/tnkr_server.py:2914`, body of `_walk_start_locked`
at `:2928`) releases the servo bus and spawns `v2_rl_walk_mujoco.py` without asking the
hardware anything. A servo that does not answer makes `turn_on()` raise inside the walk's
constructor; the traceback goes to the journal, the process exits 1, and Studio sees only
`walk_ended {exit_code: 1}`. Naveen's duck did exactly this on 2026-09-04 with servo 20
(left hip yaw) silent.

This story adds `_walk_preflight()`, called from `_walk_start_locked` **after** the rehome
and already-running guards and **before** `release_hwi(disable_torque=False)` at `:2952`,
so it reuses the server's own `HWI` handle. It is the servo half of the pre-flight described
in `_architecture.md` (System Operation, "Servo roll-call"). Story 1.2 adds the IMU half to
the same function.

The probe is the read half of `/api/motors/check` (`:751-786`): one
`read_present_position` per servo through `_io_retry`. It must **not** copy that endpoint's
gain write or its trailing `disable_torque`, because the duck may be standing in its stance
when Walk is pressed.

Refusals use the dict-detail protocol `_agent_error(status, code, message, joint)` at
`:930`, which Studio's `agent_client._request` already parses by code name. Telemetry
follows `_note_calibration_fault` (`:900`): `error_code` and `joint_name` as their own
properties on the request event, never only inside `error_message`.

## Acceptance Criteria

### Core Functionality

- [ ] **Roll-call before release**: `_walk_preflight()` runs inside `_walk_start_locked`
      under `_walk_lock`, after the `rehome_io` and already-running checks, before
      `release_hwi` and `release_state_imu`, and only on the `is_pi` path.
- [ ] **Read-only probe**: for every `(name, id)` in `hwi.joints`, one
      `hwi._io_retry(lambda i=id: hwi.io.read_present_position([i])[0], name,
      "read_present_position")` under `BUS_LOCK`. No `set_kps`, no `set_position`, no
      torque change.
- [ ] **Silent servo refuses**: any joint whose read fails after `_io_retry`'s attempts
      produces `_agent_error(502, "MOTORS_SILENT", "<n> of <total> servos did not answer:
      <names>", joint=<first silent name>)`. `Popen` is never reached.
- [ ] **Bus that will not open refuses differently**: `get_hwi()` raising produces
      `_agent_error(503, "SERVO_BUS_UNAVAILABLE", str(exc))`.
- [ ] **Healthy bus passes**: all servos answering returns a `PreflightReport` and the
      handler continues exactly as today (release, spawn, monitor thread).
- [ ] **Explicit override only**: `TNKR_SKIP_PREFLIGHT=1` in the environment skips the
      pre-flight and logs one line saying so. Nothing else skips it.

### User Experience

- [ ] **No movement on refusal**: a refused walk leaves the duck exactly as it was. No
      gain, position, or torque write happens on the refusal path.
- [ ] **Fast enough to feel like a press**: under 1 s on a healthy bus; bounded near 2 s
      with every servo silent (about 34 ms per absent servo per attempt).
- [ ] **Studio unchanged in this story**: the operator sees whatever Studio renders for
      `MOTORS_SILENT` today (story 2.2 supplies the duck sentence naming the joint).

### Technical Requirements

- [ ] **Telemetry on refusal**: `add_telemetry_props(error_code="MOTORS_SILENT",
      joint_name=<first>, silent_joints=[...], preflight_ms=<int>)` so the
      `api_request_failed` row for `/api/walk/start` is groupable.
- [ ] **Telemetry on pass**: `add_telemetry_props(preflight_ms=<int>,
      servos_responding=<total>)` on the `api_request_completed` row.
- [ ] **Existing walk tests keep passing**: `fake_walk_dir` in `tests/conftest.py`
      installs a healthy fake `HWI` (and, after 1.2, a fake state IMU) so every existing
      `POST /api/walk/start` test still spawns its script.
- [ ] **Non-Pi path untouched**: the mock walk branch (`is_pi` false) never runs the
      pre-flight.

### Technical Considerations

#### Ordering and locks

- **Before release, not after**: `release_hwi` drops the rustypot handle. Probing after it
  would open a second handle on the adapter, which is the double-open the `close()`
  docstring (`rustypot_position_hwi.py:222`) warns poisons rustypot's mutex.
- **`_walk_lock` already held**: `_walk_start_locked` runs under it; `BUS_LOCK` is taken
  inside the probe and is re-entrant, so `get_hwi()`'s own `with BUS_LOCK` is fine.
- **Same-token restart**: the already-running early return at `:2938` stays before the
  pre-flight; a running walk is not re-probed.

#### Error Scenarios to Handle

- `get_hwi()` raises (no adapter, port busy, rehome open): 503 `SERVO_BUS_UNAVAILABLE`.
- One or more joints time out through `_io_retry`: 502 `MOTORS_SILENT`, first joint in
  `joint`, all in `silent_joints`.
- A rustypot panic mid-probe: `_io_retry` already reopens the port and converts it to
  `OSError`; the joint counts as silent.
- Anything unexpected inside the probe: re-raised as 503 `SERVO_BUS_UNAVAILABLE` with the
  raw message in `error_message`. The pre-flight never lets a walk spawn past an exception
  it did not understand.

#### Performance & UX

- Healthy bus: 14 reads at 1 Mbaud, under 100 ms.
- Silent bus: 3 attempts × ~34 ms × 14 ≈ 1.4 s worst case. Acceptable for a button press.
- No prints on the success path beyond the existing `[walk_start] spawning` line.
